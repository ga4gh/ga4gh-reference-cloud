# Project Guide: GA4GH Reference Cloud Helm Deployment

## Project Overview & Architecture

Helm chart (`charts/app`) for running the refcloud in a local minikube cluster ("helm mode") or a remote Kubernetes cluster (AWS). Defaults in `values.yaml` target local minikube; AWS settings are passed as overrides at deploy time (see `README.md`).

* **Tech Stack:** Helm, Kubernetes (minikube locally), ingress-nginx, Ory Kratos & Hydra

### Directory Layout

* `charts/app/values.yaml` - chart values (local defaults)
* `charts/app/templates/_helpers.tpl` - image helpers (`refcloud.image`, `refcloud.imagePullSecrets`), security context helpers (`refcloud.podSecurityContext`, `refcloud.containerSecurityContext`) and pinned Ory image versions
* `.trivyignore.yaml` - accepted Trivy findings for the chart, each scoped to paths and with a reason
* `charts/app/templates/apps/<app>` - per-app deployments, services, config maps and migration jobs (`core-api`, `researcher-ui`, `docs`, `admin-cli`, `kratos`, `hydra`)
* `charts/app/templates/common/ingress.yaml` - ingress routes
* `.certs/` - mkcert TLS certificate generated by setup (git-ignored)

## Core Commands

Run from the repo root:

* One-time setup (shared with native mode, safe to re-run): `./scripts/refcloud-setup.sh` (`--reset` to start fresh)
* Build images, deploy and run `minikube tunnel`: `./scripts/refcloud-run-helm.sh`
* Uninstall the release: `./scripts/refcloud-run-helm.sh --down`
* Render the chart: `helm template t deploy/helm/charts/app --set image.tag=<tag>`
* Run an admin CLI command in the cluster: `kubectl exec deploy/refcloud-admin-cli -- refcloud <command>`

### Code Quality & Validation

All checks run through `./scripts/refcloud-static-analysis-helm.sh` from the repo root (bash; needs only Docker, since each tool runs from an image pinned by version and digest). CI (`.github/workflows/static-analysis-helm.yml`) calls the same script. The chart is checked with its default (local) values only.

* Run all checks: `./scripts/refcloud-static-analysis-helm.sh`
* Lint the chart (`helm lint --strict`): `./scripts/refcloud-static-analysis-helm.sh lint`
* Validate rendered manifests against the Kubernetes API schemas (kubeconform, includes the hook Jobs): `./scripts/refcloud-static-analysis-helm.sh kubeconform`
* Scan for security misconfigurations (Trivy, HIGH/CRITICAL, ignores in `.trivyignore.yaml`): `./scripts/refcloud-static-analysis-helm.sh trivy-config`
* Every ignored Trivy finding needs a `statement` (reason) and should be scoped with `paths`.

## Things to Note

* Only one local mode runs at a time: native mode's Caddy and helm mode's `minikube tunnel` both bind port 443. Both modes share the host Postgres databases.
* Ingress routes in `charts/app/templates/common/ingress.yaml` must be kept in sync with `deploy/local/Caddyfile`. Any new browser-facing path (Kratos endpoint or core-api route) needs to be added to both, or it falls through to the researcher UI.
* Never route the Hydra admin API (4445) or Kratos admin API (4434) through the ingress.
* `image.tag` is required (no default): all refcloud app images share one lockstep tag. Image repository names match the ECR repositories CI pushes to and are not parameterized.
* Ory Kratos/Hydra image versions are pinned in `_helpers.tpl` and must match `deploy/local/docker-compose.yml`.
* Migration Jobs (Liquibase, Kratos, Hydra) are Helm pre-install/pre-upgrade hooks, because a Job's pod template is immutable. They must only depend on pre-existing secrets (not chart resources such as ConfigMaps, which don't exist yet when pre-install hooks run).
* Secrets the chart expects (DB credentials, Ory secrets, OAuth client, `refcloud-tls`) are created by `scripts/refcloud-setup.sh` with the same values as native mode. Kratos and Hydra share databases with native mode, so their secrets must match `deploy/local/ory`.
* Scripts must call `kubectl`/`helm` through `kubectl_local`/`helm_local` (`scripts/lib/common.sh`), which pass the minikube context and namespace explicitly so they can never act on a remote (e.g. production) cluster.
* Pods reach host Postgres via `host.minikube.internal`.
* Every pod and container uses the security context helpers in `_helpers.tpl`: non-root, no privilege escalation, all capabilities dropped, RuntimeDefault seccomp and a read-only root filesystem. Each container mounts an `emptyDir` at `/tmp` (and any other path it writes to, e.g. researcher-ui's `/app/.next/cache`). The pod's `runAsUser` must match the image's user: core-api and admin-cli 10001, researcher-ui and Liquibase 1001, docs 101, Kratos 10000, Hydra 65532.
* Every long-running app has liveness and readiness probes, defined per template (not in values): core-api uses the actuator health groups (`/actuator/health/liveness`, `/actuator/health/readiness`, unauthenticated, plus a startup probe), Kratos `/admin/health/alive` and `/admin/health/ready` on 4434 (Kratos serves its admin API under `/admin`), Hydra `/health/alive` and `/health/ready` on 4445, docs `/`, and researcher-ui a TCP check (its pages call Kratos and Hydra). The admin CLI pod has none (`sleep infinity`).
* Server-side app code must call other services by their internal URLs (e.g. `http://refcloud-api:8080`, `http://hydra:4445`), never the public hostname: `*.localhost` resolves to the pod itself inside the cluster.
* The admin CLI runs as an idle pod (`sleep infinity`, no Service). In AWS this pod is connected to the production database, so follow the guardrails in `apps/admin-cli/CLAUDE.md`.
