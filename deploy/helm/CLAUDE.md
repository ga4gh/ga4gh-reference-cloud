# Project Guide: GA4GH Reference Cloud Helm Deployment

## Project Overview & Architecture

Helm chart (`charts/app`) for running the refcloud in a local minikube cluster ("helm mode") or a remote Kubernetes cluster (AWS). Defaults in `values.yaml` target local minikube; AWS settings are passed as overrides at deploy time (see `README.md`).

* **Tech Stack:** Helm, Kubernetes (minikube locally), ingress-nginx, Ory Kratos & Hydra

### Directory Layout

* `charts/app/values.yaml` - chart values (local defaults)
* `charts/app/templates/_helpers.tpl` - image helpers (`refcloud.image`, `refcloud.imagePullSecrets`), security context helpers (`refcloud.podSecurityContext`, `refcloud.containerSecurityContext`) and pinned Ory image versions
* `.trivyignore.yaml` - accepted Trivy findings for the chart, each scoped to paths and with a reason
* `charts/app/templates/apps/<app>` - per-app deployments, services, config maps and migration jobs (`core-api`, `researcher-ui`, `docs`, `admin-cli`, `kratos`, `hydra`, `funnel`)
* `charts/app/templates/apps/setup/` - the setup Jobs (`setup-predeploy`, `setup-postdeploy`), Helm hooks
* `setup/` - the setup Jobs' image (`refcloud-setup`): its `Dockerfile` and the `refcloud-setup` script (bash)
* `charts/app/templates/common/compute-namespace.yaml` - the compute namespace (`ga4gh.referenceCloud.compute.namespace`, default `<release>-compute`), where Funnel and the task pods run
* `charts/app/files/funnel/` - Funnel's per-task worker Job, executor Job, volume and claim templates, embedded verbatim in Funnel's config
* `charts/app/templates/common/ingress.yaml` - ingress routes
* `charts/app/templates/common/compute-connections.yaml` - the compute connections file (`connections.yml`) that core-api and the admin CLI read
* `.certs/` - mkcert TLS certificate generated by setup (git-ignored)

## Core Commands

Run from the repo root:

* One-time setup (shared with native mode, safe to re-run): `./scripts/refcloud-setup.sh` (`--reset` to start fresh)
* Build images, deploy and run `minikube tunnel`: `./scripts/refcloud-run-helm.sh`
* Uninstall the release: `./scripts/refcloud-run-helm.sh --down`
* Render the chart: `helm template t deploy/helm/charts/app --set image.tag=<tag>`
* Run an admin CLI command in the cluster: `kubectl exec deploy/refcloud-admin-cli -- refcloud <command>`

### Code Quality & Validation

All checks run through `./scripts/refcloud-static-analysis-helm.sh` from the repo root (bash; needs only Docker, since each tool runs from an image pinned by version and digest). CI (`.github/workflows/static-analysis-helm.yml`) calls the same script. The chart is checked twice: with its default (local) values, and with sample AWS values (`static-analysis/aws-values.yaml`: `cloudEnvironment: aws` with compute on). Keep every value in that file an example, never a real environment's.

* Run all checks: `./scripts/refcloud-static-analysis-helm.sh`
* Lint the chart (`helm lint --strict`): `./scripts/refcloud-static-analysis-helm.sh lint`
* Validate rendered manifests against the Kubernetes API schemas (kubeconform, includes the hook Jobs): `./scripts/refcloud-static-analysis-helm.sh kubeconform`
* Scan for security misconfigurations (Trivy, HIGH/CRITICAL, ignores in `.trivyignore.yaml`): `./scripts/refcloud-static-analysis-helm.sh trivy-config`
* Lint the setup Jobs' script (shellcheck, default checks): `./scripts/refcloud-static-analysis-helm.sh shellcheck`. Its Dockerfile is linted with the others by `./scripts/refcloud-static-analysis-deploy-local.sh`
* Every ignored Trivy finding needs a `statement` (reason) and should be scoped with `paths`.

## Things to Note

* Only one local mode runs at a time: native mode's Caddy and helm mode's `minikube tunnel` both bind port 443. Both modes share the host Postgres databases.
* Ingress routes in `charts/app/templates/common/ingress.yaml` must be kept in sync with `deploy/local/Caddyfile`. Any new browser-facing path (Kratos endpoint or core-api route) needs to be added to both, or it falls through to the researcher UI.
* Never route the Hydra admin API (4445) or Kratos admin API (4434) through the ingress. Kratos calls core-api's registration webhook directly (`http://refcloud-api:8080/webhook/kratos/...`), so that isn't routed either.
* Every Service is `type: ClusterIP`. Minikube's ingress-nginx routes to ClusterIP Services, and on AWS the ALB targets pod IPs (`alb.ingress.kubernetes.io/target-type: ip`), so nothing needs a node port. Never use `NodePort` or `LoadBalancer`: they would expose every port of the Service, admin ports included, outside the cluster.
* `image.tag` is required (no default): all refcloud app images share one lockstep tag. Image repository names match the ECR repositories CI pushes to and are not parameterized.
* Ory Kratos/Hydra image versions are pinned in `_helpers.tpl` and must match `deploy/local/docker-compose.yml`. Ory releases Kratos and Hydra with the same version number: keep them in step.
* The chart runs Kratos and Hydra **without `--dev`**, in minikube as in production, so minikube catches what production would. Without it, cookies are always `Secure`, Hydra's issuer and OAuth redirect URIs must be `https`, and Kratos hashes passwords with bcrypt cost 12 or more. Neither enforces HTTPS on in-cluster calls (that needs `serve.tls.enabled`), so plain `http://kratos:4433` and `http://hydra:444x` keep working. Native mode's compose file keeps `--dev`. Both run with `--sqa-opt-out` (no usage reports to Ory). The chart's Kratos config is production's too: keep its log level at `info` and never set `leak_sensitive_values`.
* Migration Jobs (Liquibase, Kratos, Hydra) are Helm pre-install/pre-upgrade hooks, because a Job's pod template is immutable. They must only depend on pre-existing secrets (not chart resources such as ConfigMaps, which don't exist yet when pre-install hooks run).
* **The setup Jobs** (spec 0013, Task 2; README "Setup Jobs") run `deploy/helm/setup/refcloud-setup` on every install and upgrade:
  * `setup-predeploy` connects to Postgres as the admin login in `refcloud-db-admin`: locally the local Postgres login (`refcloud-setup.sh`), on AWS `refcloud_admin` (`CREATEDB`, `CREATEROLE`, not a superuser). It creates `refcloud_admin` and that Secret itself, on a deploy where `refcloud-db-bootstrap` (the RDS master user's login, which the operator copies from Secrets Manager for that one deploy and then deletes) exists and can connect; that same deploy repairs `refcloud_admin`'s password, attributes and `ADMIN` on every app role. A bootstrap copy that can't connect (rotated) is ignored. So an environment's first deploy needs only `refcloud-db-bootstrap`, and later deploys need nothing. On Postgres 16 and later, a non-superuser admin can manage only roles it has `ADMIN` on: setup checks that for every existing app role, and grants it in a bootstrap deploy;
  * `setup-predeploy` (pre-install/pre-upgrade, weight -10, before the migrations at 0) checks or creates the Secrets, each app's database and owner role (named after the `username` in its Secret, as the connection strings are) and Data Connect's read-only role. It's the release's only pod with a ServiceAccount token: its ServiceAccount, Role (get on the Secrets it checks, by name; create on Secrets) and RoleBinding are hooks at weight -20, with `hook-succeeded`, so Helm deletes them once every pre hook has run. Keep the Role's `resourceNames` in sync with the script;
  * `setup-postdeploy` (post-install/post-upgrade) creates the researcher UI's Hydra client if it's missing, or updates the settings the chart decides where they differ (init container, `refcloud-setup` image). Those settings are the redirect URI (from `baseURL`), grant and response types, scope and auth method (`hydra_client_settings`, matching `scripts/refcloud-setup.sh`). Updates use a JSON Patch, so other fields and the secret stay. It then runs `refcloud seed` (admin CLI image, the admin CLI pod's database settings). Hydra's admin API accepts it (`network-policies.yaml`);
  * every check changes something only when it fails, and nothing is deleted. Existing Secrets are never changed; `kratos-secrets`, `hydra-secrets` and `refcloud-ui-hydra-researcher-client` are created only with a new database (Kratos and Hydra encrypt stored data with them, and Hydra keeps the client's secret). Setup's names, defaults and role settings match `scripts/lib/common.sh`, so locally (where `refcloud-setup.sh` prepares everything first) the Jobs change nothing, and the run script prints their last lines;
  * the Jobs use `before-hook-creation` only, so they're kept (with their logs) until the next deploy; `--down` and `--reset` delete them (`delete_setup_jobs`), since uninstalling leaves hooks behind. `refcloud-setup` runs as user 10001, like the admin CLI, so `setup-postdeploy`'s two images share its pod's `runAsUser`. The image installs nothing at run time (Alpine, with psql, curl, jq and bash), and is built with the lockstep tag (`REFCLOUD_IMAGES`, `push-docker-image-setup.yml`);
  * the script talks to the Kubernetes API with curl and the pod's token, and keeps secrets out of process arguments: the token through a config file descriptor, values through stdin or the environment (psql's `\getenv`), names as psql variables.
* Secrets the chart expects (DB credentials, Ory secrets, OAuth client, `refcloud-tls`, RustFS's accounts, and `refcloud-db-admin` for the setup Jobs; never `refcloud-db-bootstrap`) are created locally by `scripts/refcloud-setup.sh`, with the same values as native mode where both use them. Kratos and Hydra share databases with native mode, so their secrets must match `deploy/local/ory`. RustFS's three (`refcloud-compute-s3-root`, `-core-api`, `-funnel`) are helm-only and random, created only when missing (`create_k8s_secret_if_missing`): RustFS keeps its users with its data, which outlives the release, so they change only on `--reset`, which deletes both.
* Scripts must call `kubectl`/`helm` through `kubectl_local`/`helm_local` (`scripts/lib/common.sh`), which pass the minikube context and namespace explicitly so they can never act on a remote (e.g. production) cluster.
* Pods reach host Postgres via `host.minikube.internal`.
* **Compute:**
  * connections come only from the value `ga4gh.referenceCloud.compute.connections`, rendered into the `refcloud-compute-connections` ConfigMap and mounted into core-api and the admin CLI at `/etc/refcloud/compute/connections.yml` (`REFCLOUD_COMPUTE_CONNECTIONS_FILE`). Both read it at startup, so their pods carry a checksum of it and restart when it changes. Never set connection settings through env vars: the admin CLI wouldn't see them;
  * locally, run storage is S3 on RustFS (spec 0012): the local connection's `s3` storage, its bucket in RustFS, core-api's own RustFS user, and STS credentials limited to each run's prefix for its Nextflow Job. **Nothing in the chart mounts a `hostPath`** (that's what lets the compute namespace enforce `restricted`): keep it that way. Each task's workspace is a claim of its own from the chart's storage class (`files/funnel/storage.yaml`; the cluster's default when `ga4gh.referenceCloud.compute.storageClass` is empty), and Funnel's database is on its own claim (`funnel-db`, deleted with the release);
  * engines call core-api back at `http://refcloud-api:8080`, and WES's auth instructions URL is the docs site's `/docs/compute/access`, derived from `baseURL`;
  * **the compute namespace and Funnel render whenever compute is on** (`refcloud.computeEnabled`): always locally, and on AWS when `ga4gh.referenceCloud.compute.aws.bucket` is set (spec 0013). RustFS, Funnel's RustFS Secret (`funnel-s3`) and core-api's RustFS keys stay local only. The namespace's name is `ga4gh.referenceCloud.compute.namespace`, or `<release>-compute` (`refcloud.computeNamespace`), so two installations never clash; on AWS it must match the Pod Identity association for Funnel's workers. Nothing in it is cluster-scoped. It **enforces the `restricted` Pod Security level**, so every pod there must comply, including stand-in pods for checking the NetworkPolicies (README);
  * Funnel's job and storage templates (`files/funnel/`) are Go templates that Funnel renders per task. Helm never interprets them: `templates/apps/funnel/config-map.yaml` embeds them through `refcloud.funnelTemplate`, which only replaces the `REFCLOUD_*` placeholders and fails if one is left. Value placeholders: `REFCLOUD_FUNNEL_IMAGE`, `REFCLOUD_DEFAULT_TASK_DISK`, `REFCLOUD_SELINUX_LEVEL`. Whole-line ones, each alone on its line at its indentation, replaced with YAML or removed: `REFCLOUD_POD_PLACEMENT` (the compute pods' node selector and tolerations), `REFCLOUD_STORAGE_CLASS` and `REFCLOUD_WORKER_S3_CREDENTIALS` (locally, `files/funnel/worker-s3-credentials.yaml`). Never write template braces or placeholder names in their comments. Keep the worker's `app` and `task-id` labels: Funnel may select its Jobs by them, and the executors' `podAffinity` (their workspace claim is ReadWriteOnce) finds their worker by them;
  * Funnel (0.12.3) reads its S3 storage settings (`AmazonS3`: the connection's endpoint and region) from its config. Locally its credentials come from the workers' environment: the `funnel-s3` Secret, which the chart copies from setup's `refcloud-compute-s3-funnel` with `lookup` (setup runs before the compute namespace exists). On AWS there are no keys: workers use the `funnel-worker` ServiceAccount's role through EKS Pod Identity, and with an endpoint and a region Funnel skips its anonymous bucket-region lookup through us-east-1 (spec 0013, Task 5). Its `Kubernetes.Resources` defaults and maximums come from the chart's connection, written in `Gi` because Funnel reads them in GiB but compares them to a task's TES GB values as plain numbers. No other storage (local files included) is enabled;
  * **each worker reserves its executors' room:** it requests the task's CPU and memory (at least 256Mi), and each executor requests only 50m and up to 256Mi, limited to the task's resources. An executor must run on its worker's node (the task's claim is ReadWriteOnce), so a node autoscaler sizes or picks that node by the worker; a worker that requested only its own share could land where its executor never fits, and the executor would wait forever (spec 0013, Task 8). Keep it that way, and the quota's per-task sizes in sync;
  * the worker's root filesystem is writable (`WorkDir: /tmp`): Funnel 0.12 stages outputs next to the task's workspace, in `WorkDir` itself, where it allows no other mount. The executors' stays read-only;
  * Funnel's server, its workers and the executors all run as user and group 10001. Executors must too: with capabilities dropped, another user can't write to the worker's files;
  * **never give Funnel permission on ServiceAccounts, or on PersistentVolumes.** A task's `_WORKER_SA` tag names a ServiceAccount Funnel uses (and 0.11 deleted at clean-up); core-api refuses `_` tags, but the permission shouldn't exist either. With per-task claims from the StorageClass, Funnel never touches PersistentVolumes (spec 0012); stage 2's cluster-wide permission is gone;
  * Funnel's image is pinned in `_helpers.tpl` (`refcloud.funnelImage`, version and multi-architecture digest); keep the version in sync with `deploy/local/funnel/Dockerfile`;
  * the chart's own connection is defined once, in `templates/common/_compute.tpl`: `nextflow-funnel-kubernetes-local` (`refcloud.localComputeConnection`, RustFS) or, on AWS, `nextflow-funnel-kubernetes-aws` (`refcloud.awsComputeConnection`, from `ga4gh.referenceCloud.compute.aws`: the bucket, region, run role and compute's private S3 endpoint from the infra repo's Terraform output, and the engine's size and limits). `refcloud.computeConnection` picks one, and the connections file, the compute namespace's ResourceQuota (`templates/common/compute-resource-quota.yaml`, computed from its limits with half again as headroom, so it follows them), its LimitRange and Funnel's config all read it. Both share `refcloud.computeEngine`: the Nextflow and nf-ga4gh versions, which must match the Nextflow image's (`compute/images/nextflow/Dockerfile`), which refuses to run otherwise; the image (`refcloud-nextflow` with the lockstep tag); and where the Jobs run; The quota also counts the workers' and executors' sizes beyond each task's resources, Funnel's server, and the storage claims (each task's workspace at most `max-task-disk-gb`, and `funnel-db`): keep them in sync with `files/funnel/worker-job.yaml`, `templates/apps/funnel/deployment.yaml` and `funnel-db.yaml`. With the quota, every pod in the compute namespace must set CPU and memory requests and limits;
  * core-api runs as its own ServiceAccount (`refcloud-api`), whose Role in the compute namespace (`templates/apps/core-api/rbac.yaml`) covers only what `NextflowKubernetesEngine` does: Jobs, pods (get, list, delete) and Secrets (create, delete). Keep it that narrow; no pod logs or exec. The connection's health check asks the API server about each permission in `NextflowKubernetesEngine.REQUIRED_PERMISSIONS`: keep the two in sync;
  * the Nextflow Jobs call core-api's TES API through the engine callback URL, which is fully qualified (`http://refcloud-api.<release namespace>.svc:8080`) because short names don't resolve from the compute namespace. core-api's NetworkPolicy accepts them (pods labelled `app.kubernetes.io/name: refcloud-nextflow` in the compute namespace);
  * **the compute namespace denies all traffic in and out by default** (`templates/common/compute-network-policies.yaml`, with a table in its header), then allows each component only what it needs, by its `app.kubernetes.io/name` label: keep the labels in `files/funnel/` and `NextflowKubernetesEngine` in sync with it. **Workflow pods (the Nextflow Jobs and Funnel's executors) get no DNS**, since lookups of made-up names would carry data out through kube-dns: core-api resolves its own address for the Nextflow Job's TES endpoint, and pins the run storage endpoint's name in the Job's `/etc/hosts` (`hostAliases`), keeping the name so TLS works (AWS's interface endpoint). They get DNS, and the listed destinations, only through `ga4gh.referenceCloud.compute.outgoingAllowlist`. Funnel's workers keep DNS (they find Funnel's server by name). On AWS the run storage rules allow compute's private S3 endpoint at its fixed addresses (`compute.aws.s3EndpointIps`), and the workers also the Pod Identity agent (`169.254.170.23:80`). **The Kubernetes API and DNS rules name both address forms**, so they work under minikube's Calico (which matches a Service's traffic after its translation) and EKS's policy agent (which matches the address the pod connects to; spec 0013, Task 5): the `kubernetes` Service's cluster IP and the API server's own addresses, and kube-dns's pods plus CoreDNS's address, the `.10` next to that Service's `.1` (EKS Auto Mode runs CoreDNS on every node, with no kube-dns pods). They're looked up when the chart is deployed (`refcloud.computeClusterAddresses`; `helm template` renders the rules without them, and a deploy that finds no API server fails);
  * **where compute pods run, and their SELinux level:** `ga4gh.referenceCloud.compute.nodeSelector` and `tolerations` (on AWS, the environment's compute node pool) go into the Nextflow Jobs (the connection's engine `node-selector` and `tolerations`, applied by `NextflowKubernetesEngine`) and Funnel's worker and executor templates, not Funnel's server. Every compute pod shares one SELinux level (`refcloud.computeSelinuxLevel`: the value `seLinuxLevel`, or derived from the compute namespace's name): on nodes that enforce SELinux (EKS Auto Mode), a task's worker and executors could otherwise not share its workspace claim (spec 0013, Task 5). Minikube ignores it. They all carry `karpenter.sh/do-not-disrupt`, so node autoscalers never move a running task. Task claims and `funnel-db` use `ga4gh.referenceCloud.compute.storageClass` (the cluster's default when empty; `ebs-gp3` on AWS);
  * the compute namespace's LimitRange (`templates/common/compute-limit-range.yaml`) gives defaults to containers that set no CPU or memory, and caps each container at the largest the chart's connection allows;
  * the local connection's limits are sized for minikube's default container (2 CPUs, about 6 GB), next to the release (3.3 GB at rest): one run at a time and 1 GB of tasks in flight. Raising them needs a bigger minikube;
  * **RustFS** (`templates/apps/rustfs/`, local only; spec 0012) is the S3-compatible server that stands in for S3: the local connection keeps its runs in its `refcloud-compute` bucket (`refcloud.localComputeBucket`). It runs in the release namespace, pinned in `_helpers.tpl` (`refcloud.rustfsImage`). Its data claim (`rustfs-data`) has `helm.sh/resource-policy: keep`, so run outputs survive `--down`, and `--reset` deletes it. A post-install/post-upgrade hook Job (`rustfs-setup`) creates the bucket and the `core-api` (`runs/*`, `health/*`) and `funnel` (`runs/*`) users and policies with RustFS's own CLI; it's safe to re-run, and it alone uses the root account. RustFS accepts only core-api, that Job, and the compute namespace's Nextflow Jobs and Funnel workers (`network-policies.yaml`, `compute-network-policies.yaml`);
  * `refcloud-run-helm.sh` registers the demo platform `nextflow-demo-kubernetes` after deploying, through the admin CLI pod (only the cluster sees the chart's connections), with no per-user limits so the connection's apply. `--down` keeps RustFS's data claim (`rustfs-data`) and its Secrets, so runs' files survive; `--reset` (`reset_kubernetes`) deletes both after uninstalling the release. Funnel's per-task claims belong to their worker Jobs, and everything else goes with the compute namespace, so nothing else needs clearing.
* Every pod and container uses the security context helpers in `_helpers.tpl`: non-root, no privilege escalation, all capabilities dropped, RuntimeDefault seccomp and a read-only root filesystem. Each container mounts an `emptyDir` at `/tmp` (and any other path it writes to, e.g. researcher-ui's `/app/.next/cache`). The pod's `runAsUser` must match the image's user: core-api, admin-cli and refcloud-setup 10001, researcher-ui and Liquibase 1001, docs 101, Kratos 10000, Hydra 65532. Funnel's image runs as root by default; the chart runs it as 10001 (user and group) to own the compute storage.
* **core-api runs exactly one pod** (`replicas: 1`, `strategy: Recreate`): compute serializes its work with in-process locks, so two instances, even briefly during a rolling update, could launch a run twice, prepare a run's inputs twice, or admit tasks past the pooled limits. A deploy or restart therefore leaves a short gap with no API. More replicas need database locks first (spec 0011, Future Directions).
* Every long-running app has liveness and readiness probes, defined per template (not in values): core-api uses the actuator health groups (`/actuator/health/liveness`, `/actuator/health/readiness`, unauthenticated, plus a startup probe), Kratos `/admin/health/alive` and `/admin/health/ready` on 4434 (Kratos serves its admin API under `/admin`), Hydra `/health/alive` and `/health/ready` on 4445, docs `/`, and researcher-ui a TCP check (its pages call Kratos and Hydra). The admin CLI pod has none (`sleep infinity`).
* NetworkPolicies (`templates/common/network-policies.yaml`) let each pod accept only the traffic it needs; the Kratos and Hydra admin APIs accept only the pods that use them. **A new in-cluster caller (a new internal URL in a deployment or config map, or a new app) needs a rule there**, or its requests time out. Keep the table in the template's header up to date. Minikube enforces them with Calico (`start_minikube` creates clusters with `--cni=calico`; `require_minikube_calico` refuses older clusters). On AWS, `networkPolicy.ingressFrom` is required, and EKS Auto Mode's Network Policy Controller must be on (README).
* Server-side app code must call other services by their internal URLs (e.g. `http://refcloud-api:8080`, `http://hydra:4445`), never the public hostname: `*.localhost` resolves to the pod itself inside the cluster.
* The admin CLI runs as an idle pod (`sleep infinity`, no Service). In AWS this pod is connected to the production database, so follow the guardrails in `apps/admin-cli/CLAUDE.md`.
