# Explore 1000 Genomes Data Via DRS API

In this demo, you will explore API-based controlled data access in a standardized GA4GH environment. You will inspect and download files from the 1000 Genomes dataset via the Reference Cloud's **DRS API**, using your **Passport** token to obtain authorization. You will explore all endpoints of the DRS API, using both single-object and bulk-object requests to access the underyling data.

This demo assumes you have familiarity with:
* Your local machine's command line
* HTTP
* REST APIs

If you have not already done so, please install a REST API testing tool on your local machine, such as:
* `curl` for terminal-based REST API calls (plus `jq` for output formatting)
* [Postman](https://www.postman.com/) for GUI-based REST API calls

## Obtaining Access to the 1000 Genomes Dataset

To begin, log in to the [reference cloud](https://refcloud.ga4gh.org) and visit the **Browse Datasets** page. You **must** be approved to access the **1000 Genomes** dataset to continue with the demo (this will be indicated by an "Approved" badge beside "Access Status").

## Obtaining DRS IDs

DRS acts strictly as a **data access** API. When a researcher has a specific **DRS ID**, they may provide that ID to the DRS API to obtain file metadata as well as access methods to download the file. However, DRS is not a **discovery** API, meaning that it does not provide any way for researchers to search for new DRS IDs. Typically, DRS ID discovery is handled by other GA4GH APIs, such as Beacon or Data Connect (this will be explored in future demos).

Fortunately, the reference cloud has a built-in way to discover DRS IDs. Navigate to the [DRS page](https://refcloud.ga4gh.org/drs) and select **1000 Genomes** from the dropdown menu to render a table of DRS IDs. Each row represents all DRS Objects associated with the exome sequencing files for a single individual (BAM, BAI, CRAM, CRAI, etc).

<CenteredImage src={OneThousandGenomesDrsObjectTableImage} alt="1000 Genomes DRS Object Table" maxWidth="85%" />

In the next step, we will supply some of these IDs to the DRS API to obtain metadata and access methods for each file. Please keep the table of DRS IDs open in your browser as we will refer back to it.

## DRS Part 1: Locating the DRS API and Service Info

To begin, select one DRS ID from the table. We recommend choosing the ID for the BAM File in the first row, as that's what we'll be using for this section. That ID is:

> `HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam`

Now we're ready to begin using DRS. The base URL for the reference cloud's DRS API is:

> `https://refcloud.ga4gh.org/ga4gh/drs/v1`

Confirm you can reach the DRS API by making a `GET` request to the **Service Info** endpoint:

<HttpsCurlCodeBlock
  curlCommand="curl -s -X GET https://refcloud.ga4gh.org/ga4gh/drs/v1/service-info | jq"
  httpsRequest="GET https://refcloud.ga4gh.org/ga4gh/drs/v1/service-info HTTP/2"
/>

You should receive a response with a `200 OK` status, and a JSON payload that looks like this:

```
{
  "id": "org.ga4gh.refcloud.drs",
  "name": "GA4GH Reference Cloud DRS Service",
  "type": {
    "group": "org.ga4gh",
    "artifact": "drs",
    "version": "1.5"
  },
  "description": "GA4GH reference implementation of the Data Repository Service (DRS) specification",
  "organization": {
    "name": "Global Alliance for Genomics and Health",
    "url": "https://ga4gh.org"
  },
  "contactUrl": "mailto:jeremy.adams@ga4gh.org",
  "documentationUrl": "https://github.com/ga4gh/ga4gh-reference-cloud",
  "createdAt": "2026-07-20T12:00:00Z",
  "updatedAt": "2026-07-20T12:00:00Z",
  "environment": "production",
  "version": "0.1.0",
  "drs": {
    "maxBulkLengthRequest": 10
  }
}
```

This payload provides basic metadata about the DRS service itself, including the service name, description, and the organization maintaining it. Most importantly, it indicates which version of the DRS specification that the reference cloud has implemented (version 1.5). This information provides researchers with a clear indication of what operations and request types the service supports!

**Note:** Service Info is another GA4GH specification that provides standardized metadata about running web services. All GA4GH API specifications (i.e. DRS, WES, TRS, Beacon, refget, htsget, RNAget, etc.) have implemented the Service Info standard. This allows GA4GH to maintain a registry of standardized services around the world, supporting a decentralized, federated network of systems.

## DRS Part 2: Authorization Info

Now let's make an API call to the DRS API's `/objects/{objectId}` endpoint using our selected DRS ID of `HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam`:

<HttpsCurlCodeBlock
  curlCommand="curl -i -s -X GET https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam"
  httpsRequest="GET https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam HTTP/2"
/>

You should see a returned status of `401 Unauthorized`, indicating that our request failed because we did not provide any authorization token. Fortunately, DRS provides an **Authorization Info** endpoint that informs us how to obtain the auth token.

Instead of submitting a `GET` request, submit an `OPTIONS` request to the same URL, i.e.

<HttpsCurlCodeBlock
  curlCommand="curl -s -X OPTIONS https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam | jq"
  httpsRequest="OPTIONS https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam HTTP/2"
/>

You should receive the following response payload:

```
{
  "drs_object_id": "HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam",
  "supported_types": [
    "BearerAuth",
    "PassportAuth"
  ],
  "passport_auth_issuers": [
    "https://refcloud.ga4gh.org"
  ],
  "bearer_auth_issuers": [
    "https://refcloud.ga4gh.org"
  ]
}
```

Our request didn't return the DRS Object itself, but rather the Authorization Info controlling access to the DRS Object we are interested in. The response tells us 2 things:
1. We can use either `BearerAuth` or `PassportAuth` authorization methods to obtain the DRS Object
2. In both cases, the DRS API only trusts JWT tokens that have an **issuer** of `https://refcloud.ga4gh.org`

This means we have to obtain our authorization token from `https://refcloud.ga4gh.org` to access the DRS Object. Visit the [Reference Cloud's "View Passport Token" page](https://refcloud.ga4gh.org/passport) and click the **Copy** button to copy the passport token to your clipboard. We will use this token for the remainder of the demo.

<CenteredImage src={OneThousandGenomesDemoCopyPassportTokenImage} alt="1000 Genomes Demo Copy Passport Token" maxWidth="85%" />

**Note:** If you are running through this demo using curl, you can even set your passport token to an environment variable in your terminal:

```
export PASSPORT_TOKEN="<your_passport_token>"
```

## DRS Part 3: Single-Object Requests

### Bearer Auth Method

Now let's retry our original `GET` request, except this time we will supply our Passport token as a standard OAuth 2.0 Bearer token.

<HttpsCurlCodeBlock
  curlCommand={`curl -s -X GET "https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam" \\
    -H "Authorization: Bearer \${PASSPORT_TOKEN}" | jq`}
    
  httpsRequest={`GET https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam HTTP/2 \
  Authorization: Bearer <your_passport_token>`}
/>

You should receive a response with a status of `200 OK`, and with a payload that represents the DRS Object:

```
{
  "id": "HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam",
  "name": "HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam",
  "self_uri": "drs://refcloud.ga4gh.org/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam",
  "size": 9196950908,
  "created_time": "2015-05-13T07:30:44",
  "updated_time": "2015-05-13T07:30:44",
  "version": "v1",
  "mime_type": "application/octet-stream",
  "checksums": [
    {
      "checksum": "9a835311cdd5482fd7915590c88cd65b-69",
      "type": "etag"
    }
  ],
  "access_methods": [
    {
      "type": "https",
      "access_url": {
        "url": "https://1000genomes.s3.us-east-1.amazonaws.com/phase3/data/HG00096/exome_alignment/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam"
      },
      "cloud": "aws",
      "region": "us-east-1",
      "available": true
    }
  ],
  "description": "HG00096 whole-exome bam file",
  "aliases": [
    "HG00096 whole-exome bam file"
  ]
}
```

Excellent work! You have just obtained your first DRS Object via the DRS API!

### Passport Auth Method

We can also obtain this DRS Object using the **Passport Auth** method, which involves making a `POST` request to the same URL. Instead of providing the passport token in an Authorization header, we will provide it in the request body itself, as the single entry in the `passports` array:

<HttpsCurlCodeBlock
  curlCommand={`curl -s -X POST "https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam" \\
    -H "Content-Type: application/json" \\
    -d "{\\"passports\\":[\\"\${PASSPORT_TOKEN}\\"]}" | jq`}
  httpsRequest={`POST https://refcloud.ga4gh.org/ga4gh/drs/v1/objects/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam HTTP/2
  Content-Type: application/json
  
  {"passports":["<your_passport_token>"]}`}
/>

You should receive a response containing the exact same DRS Object payload.

**Note:** DRS supports both `GET` (BearerAuth) and `POST` (PassportAuth) methods for obtaining a single DRS Object. The `POST` method allows for very large passport tokens which can sometimes exceed the allowed length of an HTTP Authorization header. In our case, we can use either method to access the same DRS Object.

### Accessing Raw Files

We have now seen that a request to the `/objects/{objectId}` endpoint returns basic metadata for a single DRS Object, such as object id, name, description, checksums, and file size. But we can also use this reponse payload to obtain the raw file itself.

Within the DRS Object response is a property called `access_methods`, which contains an array of DRS **Access Methods**. Each access method contains a URL (and potential authorization headers) for fetching the raw file. Researchers can use their preferred access method to fetch the data and stage it for an analysis. In our case, the DRS Object contains only 1 access method:

```
...
"access_methods": [
  {
    "type": "https",
    "access_url": {
      "url": "https://1000genomes.s3.us-east-1.amazonaws.com/phase3/data/HG00096/exome_alignment/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam"
    },
    "cloud": "aws",
    "region": "us-east-1",
    "available": true
  }
],
...
```

The access method above indicates that the raw file is sitting in an AWS S3 bucket in the us-east-1 region and can be accessed via `https`. Since no authorization headers are provided, we do not need to supply any to fetch the file.

To fetch the file, simply make a request to the provided URL and save the output as a file:

<HttpsCurlCodeBlock
  curlCommand={`curl -X GET \\
    -o HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam \\
    "https://1000genomes.s3.us-east-1.amazonaws.com/phase3/data/HG00096/exome_alignment/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam"`}
  httpsRequest={`GET https://1000genomes.s3.us-east-1.amazonaws.com/phase3/data/HG00096/exome_alignment/HG00096.mapped.ILLUMINA.bwa.GBR.exome.20120522.bam HTTP/2`}
/>

Great! You have now used the DRS API to fetch not only DRS Object metadata, but the underlying file itself!

## Conclusion

In this demo, you learned how to:
* use the **Service Info** endpoint to learn more about a DRS service
